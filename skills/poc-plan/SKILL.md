# PoC Plan — PoC / 试点管理知识库

B 端销售的"决战环节"。PoC 没赢，合同就没了。

---

# 一、PoC 的"四个为什么"

```
1. 为什么客户要 PoC？
   → 决策风险大、对你不熟悉、内部需要数据说服

2. 为什么我们做 PoC？
   → 不是为了"展示"，而是要"赢得" Decision Maker

3. 为什么 PoC 失败率高？
   → 范围模糊 + 验收主观 + 客户不付承诺感

4. 为什么 PoC 必须有时间盒？
   → 客户不签 + 你不甘心 = 永久试用 = 销售杀手
```

# 二、PoC 资格预审（避免白嫖）

接到客户 PoC 请求时，先用三道筛子：

```
筛 1：预算确认
  ✅ 客户已经有预算或愿意申请
  ❌ "成功了再说" / "看效果再批"

筛 2：决策链清晰
  ✅ DMU 已知 + 高管参与
  ❌ "技术总监说算" / 高管不见面

筛 3：转正路径清晰
  ✅ 成功后明确签合同时间
  ❌ "看公司情况"

三筛不全过 → 不做 PoC，仅 Demo
```

# 三、范围谈判：最关键一步

## 3.1 范围三层结构

```
Must Have（必验证）：
  - 技术：核心集成 / 性能 / 安全
  - 业务：1-3 个核心用例

Should Have（推荐验证）：
  - 1-2 个扩展场景
  - 1-2 个高级功能

Won't Have（明确排除）：
  - 客户额外想要的（写入"后续合同范围"）
  - 定制开发（除非额外付费）
  - 复杂数据迁移（用样本数据即可）
```

## 3.2 范围谈判常见博弈

```
客户："我想验证所有功能"
应对："PoC 是验证关键决策风险，不是替代正式合同。我们抓 3 个最重要的"

客户："我想 100 个用户测"
应对："PoC 用 20 人覆盖典型角色，正式签约后再全员"

客户："我想集成 5 个系统"
应对："PoC 集成 1 个最重要的，证明能集成 + 性能。其他写入合同"

客户："我想要定制开发"
应对："PoC 用标准产品。如必须定制，单独 SOW + 付费"
```

# 四、成功标准设计

## 4.1 必须四要素

```
1. 量化（Specific + Measurable）
   ❌ "效率提升"
   ✅ "效率从 X 单/天 提升到 Y 单/天"

2. 时限（Time-bound）
   ❌ "实现"
   ✅ "在 PoC 第 4 周末"

3. 阈值（Pass / Fail 明确）
   ❌ "比较好"
   ✅ "P95 < 500ms"

4. 双方签字（不可口头）
   书面 + 双方决策人签字
```

## 4.2 标准结构

```
| 维度 | 指标 | 必达 | 优秀 |
|------|------|------|------|
| 技术 1 | ... | ≥ X | ≥ Y |
| 技术 2 | ... | ... | ... |
| 业务 1 | ... | ... | ... |
| 业务 2 | ... | ... | ... |
| 用户 | NPS | ≥ +30 | ≥ +50 |

成功定义：N 项至少 M 项必达
失败定义：< M-1 项必达
```

# 五、PoC SOW 关键条款

```
1. 范围（Scope）
   - In Scope（详细列出）
   - Out of Scope（详细列出，避免博弈）

2. 成功标准（Acceptance Criteria）
   - 量化 + 时限 + 双方签字

3. 双方责任
   - 我方提供：环境 / 人 / 培训 / 文档
   - 客户提供：数据 / 账号 / 关键人 / 时间

4. IP 归属
   - 我方代码：归我方
   - 客户业务流：归客户
   - 测试数据：PoC 后销毁

5. 费用
   - 完全免费（条件：成功签合同）
   - 象征性付费（成功后抵扣）
   - 完全付费（大量定制场景）

6. 时间盒
   - 开始 + 结束日期
   - 中期评审日期
   - 转正决策日期

7. 退出机制
   - 成功 → 进入合同谈判
   - 失败 → 体面收尾
   - 中止 → 任一方书面通知

8. 数据保护
   - 数据使用范围
   - PoC 后处理（删除 / 返还）

9. 保密
   - 双方保密义务
   - PoC 期间不得对外宣传

10. 法律
    - 适用法律
    - 争议解决
```

# 六、PoC 计费策略

## 6.1 三种模式

```
A. 完全免费 PoC
   适合：销售推动 / 战略客户
   风险：客户无承诺感 / 可能白嫖
   缓解：转正 30 天内承诺

B. 象征性付费（推荐）
   金额：¥X 万 / 月费的 10-30%
   含义：客户有承诺感
   规则：成功签合同后从总价抵扣
   适合：标准 B 端

C. 完全付费 PoC
   适合：要求大量定制 / 无意立即签合同
   含义：把咨询服务化
   适合：大型企业 / 政府
```

## 6.2 选择决策树

```
战略客户 + 销售推动 → A
有合同承诺 + 标准产品 → B（推荐）
要求定制 / 长 PoC → C
```

# 七、关键节点 + 验收会

## 7.1 周会节奏

```
W0：Kick-off（90 分钟）
  - 范围 + 成功标准签字
  - 时间表 + 责任分工
  - 沟通节奏

每周：Sync 会（30 分钟）
  - 进度 + 阻塞 + 升级
  - 下周计划

中期 Review：
  - 数据中期评分
  - 风险审议
  - 范围是否调整

末次验收：
  - 6 维度最终数据
  - 双方签字
  - 转正决策
```

## 7.2 决策人参与原则

```
✅ 必须：Champion 全程 + DM 关键节点
✅ 推荐：高管参加 Kick-off + 末次验收

❌ 反模式：仅技术对接 / 高管不出现
原因：PoC 成功不等于签约成功
```

# 八、转正合同 SOP

```
末次验收成功 → 立即启动（不超 30 天）

Day 0：末次会议签字
Day 1：Proposal 发送（Multi-Year 折扣）
Day 3：与 DM 一对一谈判
Day 7：商务条款对齐
Day 14：法务条款对齐
Day 21：合同终稿
Day 28：财务付款
Day 30：正式 Kick-off

关键技巧：
  ✅ 趁热打铁（不超 30 天）
  ✅ Multi-Year 折扣锁定
  ✅ Champion 内部背书 + 帮你推进
  ✅ 高管 EBR 锁定战略
```

# 九、失败 PoC 体面退出

## 9.1 失败 ≠ 撕破脸

```
PoC 失败原因可能是：
  - 我方产品确实不匹配（接受）
  - 客户内部变化（不可控）
  - 范围设计有问题（学习）
  - 关键人变动（环境）

无论原因，体面退出 = 留下"未来机会"
```

## 9.2 体面收尾 SOP

```
Day 0：末次会议确认失败（不甩锅）

Day 1：发详细分析报告
  - 哪些达标 / 哪些未达标
  - 我方诊断
  - 改进路线图（不卑不亢）

Day 7：体面收尾会议
  - 总结 + 致谢
  - 数据 / 系统 / 资料移交
  - 留下未来机会窗口

6 个月后：评估重启
  - 我方是否已改进达标？
  - 客户场景是否变化？
  - 关键人是否变动？
```

# 十、常见陷阱与避免

| 陷阱 | 表现 | 避免 |
|------|------|------|
| 无限延长 PoC | 12 月还在试用 | 时间盒 + 失败定义都签字 |
| 范围爆炸 | 客户不断加要求 | 任何额外 = 新 SOW |
| 免费定制开发 | 为客户写代码 | 只用标准产品 |
| 验收标准模糊 | "效果不错" | 量化 + 双签 |
| 客户不付费 | 完全免费 = 没承诺 | 象征性付费 |
| Champion 失踪 | 销售压力下急 | Kick-off 锁定 |
| DM 不出席 | 仅技术对接 | 末次验收必须 DM |
| PoC 后拖延 | 客户找借口 | 30 天 SOP |

# 十一、批量 PoC 池管理

```
公司有多个并行 PoC 时：

✅ Tier 化（按客户价值分级）
✅ PreSales 资源配额（防止过载）
✅ 每周 PoC 健康度复盘
✅ 转化率追踪（PoC → 合同）
✅ 失败原因归类 → 产品改进
```
