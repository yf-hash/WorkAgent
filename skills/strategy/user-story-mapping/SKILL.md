# User Story Mapping — 用户故事地图知识库

将一句话需求拆解为可发布的故事切片，让团队从用户视角而非功能视角对齐范围。

---

# 一、为什么需要故事地图

```
传统需求列表（List）：
  ┌──────┐
  │ 功能1 │
  │ 功能2 │  ← 看不出业务流程
  │ 功能3 │  ← 看不出取舍优先级
  │ ...  │  ← 看不出发布切片
  └──────┘

用户故事地图（Map）：
  Backbone:  [活动1] ─→ [活动2] ─→ [活动3]   ← 用户旅程的骨干
  Tasks:      task    task     task          ← 完成活动的具体任务
  Stories:    s1 s2   s3 s4    s5 s6        ← MVP/V1/V2 切片
  ─────────────────────────────────────────
  R1 (MVP):   s1      s3       s5           ← 最小可用切片
  R2:         s2      s4       s6
  R3:                 (s7)     (s8)
```

# 二、Story Map 三层结构

## 2.1 Backbone（骨架层）

时间轴 + 大活动顺序，回答：**用户从开始到完成目标，经历了哪些阶段？**

例（电商购物）：
```
[发现需求] → [搜索商品] → [评估比较] → [下单支付] → [收货验货] → [复购/分享]
```

骨架原则：
- ≤ 7-9 个活动（认知负荷上限）
- 用动词短语，不是名词
- 跨"组织/系统"边界要可见

## 2.2 Tasks（任务层）

每个活动下展开：**用户为完成这个活动做了哪些具体动作？**

例（搜索商品 活动下）：
```
[搜索商品]
  ├─ 输入关键词
  ├─ 应用筛选（价格/品类/品牌）
  ├─ 切换排序（综合/销量/价格/评价）
  ├─ 浏览搜索结果
  └─ 点击商品详情
```

任务原则：
- 用户视角的动作，而非系统功能
- 可被单个用户故事覆盖
- 颗粒度大致相当

## 2.3 Stories（故事层）

每个 Task 下进一步拆分为可独立交付的用户故事：

```
[应用筛选]
  ├─ 按价格区间筛选 (P0)
  ├─ 按品牌筛选 (P1)
  ├─ 按评分筛选 (P2)
  ├─ 多条件组合筛选 (P2)
  └─ 保存筛选条件 (P3)
```

# 三、用户故事写法

## 3.1 三句式模板

```
作为 <角色>
我想 <动作>
以便 <价值>
```

例：
```
作为新用户
我想在搜索结果里按"评分 4.5+"筛选
以便快速找到口碑好的商品，避免踩雷
```

## 3.2 INVEST 原则

| 字母 | 含义 | 检查点 |
|------|------|--------|
| **I**ndependent | 独立 | 可独立开发不依赖其他故事 |
| **N**egotiable | 可协商 | 不固化解决方案，留有讨论空间 |
| **V**aluable | 有价值 | 对用户或客户有可见价值 |
| **E**stimable | 可估算 | 团队能给出大致工作量 |
| **S**mall | 小 | 1-2 个 Sprint 内可完成 |
| **T**estable | 可测试 | 有明确验收标准 |

## 3.3 验收标准（Given/When/Then）

```
Given：[前置条件]
When：[用户操作]
Then：[预期结果]
And：[附加验证]
```

例：
```
Given：我在搜索结果页，已搜索"耳机"
When：我点击"评分 4.5+"筛选
Then：列表只显示评分 ≥ 4.5 的商品
And：筛选标签显示在顶部，可点击 X 清除
And：URL 参数同步更新，可分享/收藏
```

# 四、Walking Skeleton（行走骨架）

> "可以行走的骨架"：跨越所有 Backbone 活动的最小端到端切片，让用户能完整走完一个流程。

设计原则：
```
✅ 端到端跑通，每个 Backbone 活动至少有一个故事
✅ 故事尽可能简单，能"走"就行（不要漂亮）
✅ 严格控制范围，敢说"这个版本不做"
✅ 从骨架学习真实使用，再决定 V2 加什么
```

例（电商 Walking Skeleton）：
```
[发现需求]    → [搜索]      → [评估]    → [下单]      → [收货]
   ↓             ↓             ↓           ↓            ↓
首页推荐10个    关键词搜索    商详页+1张   微信支付      地址填写+
（无个性化）    （无筛选）    主图+价格     （无优惠券）  默认快递
```

# 五、Release Slices（发布切片）

横线切分故事地图，决定哪些故事进入 R1/R2/R3：

```
                Activity1   Activity2   Activity3   Activity4
Tasks:          T1.1 T1.2   T2.1 T2.2   T3.1 T3.2   T4.1 T4.2
              ─────────────────────────────────────────────────
R1 (MVP):       s1   --     s3   --     s5   --     s7   --
              ─────────────────────────────────────────────────
R2:             s2   s2'    s4   --     s6   s6'    s7'  --
              ─────────────────────────────────────────────────
R3 (Polish):    --   --     --   s4'    --   --     --   s8
              ─────────────────────────────────────────────────
```

切片原则：
- R1：Walking Skeleton，端到端跑通
- R2：扩大每个活动的覆盖度
- R3：体验优化、边缘场景、个性化
- R4+：增长功能、平台化能力

# 六、Three Amigos 三方对齐

每个故事拆分前，PM + Dev + QA 一起对齐：

```
PM 视角  →  这个故事的用户价值是什么？谁会用？
Dev 视角 →  实现成本？技术风险？依赖什么？
QA 视角  →  怎么测试？边界条件？回归影响？
```

输出：
- 故事描述（PM 主笔）
- 验收标准（QA 主笔，PM 确认）
- 技术拆分（Dev 主笔，PM 同意）

# 七、Story Mapping 工作坊流程

```
Step 1: 召集（90-180 分钟，PM + Dev + 设计 + 业务）
Step 2: 设定北极星（这次工作坊聚焦哪个目标）
Step 3: 写下 1-3 个核心用户角色
Step 4: 沿时间轴写 Backbone（每人独立写 → 合并 → 排序）
Step 5: 每个 Backbone 下展开 Tasks（亲和图分组）
Step 6: 每个 Task 下穷举 Stories（贴便利贴）
Step 7: 优先级讨论（P0/P1/P2 + 排除项）
Step 8: 切发布线（R1/R2/R3）
Step 9: R1 故事点估算 + 风险标注
Step 10: 拍照存档 + 转化为数字化故事地图
```

# 八、典型陷阱与避免

| 陷阱 | 表现 | 避免方法 |
|------|------|---------|
| 功能视角 | "登录模块"、"支付系统" | 改成用户动作"我登录"、"我支付" |
| 颗粒度混乱 | Story 跨度从 1h 到 1 月 | INVEST + Sprint 内可完成 |
| 一次画完即冻结 | 地图 6 个月不更新 | 每个 Sprint 末刷新 R2/R3 |
| 缺少异常路径 | 只画 Happy Path | 每个 Task 至少考虑 1 个异常 |
| 故事写得太宽泛 | "用户体验更好" | 用 3 句式 + Given/When/Then |
| 无验收标准 | 开发完才发现理解不一致 | 故事拆分时同步写 AC |
