# Tech Debt Prioritization Skill

## 核心原则

1. **技术债不是 Bug 也不是新功能**——它是"过去为了赶时间欠下的本"，今天还本会让明天速度提升。
2. **不是工程团队私事**——PM 要参与优先级讨论，因为还本会占用做新功能的时间。
3. **不还本 = 复利积累**——某天突然某个功能完全做不动 / SLO 不达标 / 安全事件。
4. **PM 不懂技术也要懂代价**——用业务语言量化（多久能交付一个新功能 / 客户投诉率 / 故障频率）。

## 技术债分类（7 类）

| 类别 | 描述 | 例子 |
|------|------|------|
| 1. **架构债** | 系统设计不当 | 单体应该拆服务、数据库选错 |
| 2. **代码债** | 实现层质量低 | 复杂度高、重复代码、缺设计模式 |
| 3. **测试债** | 测试覆盖不足 | 单测 < 60%、无集成测试、无 E2E |
| 4. **文档债** | 文档缺失或过期 | API 文档与实际不符、无架构文档 |
| 5. **基础设施债** | 部署 / 监控 / 工具落后 | 手工部署、无监控、CI 龟速 |
| 6. **安全债** | 已知漏洞未修 | 依赖库 CVE、SQL 注入风险 |
| 7. **数据债** | 数据模型 / 质量问题 | 字段含义漂移、关联表无主键 |

## 影响打分（每条债务必填）

### 三维评分（1-5）

| 维度 | 解释 |
|------|------|
| **速度影响** | 不还本，每做一个新功能多耗 X% 时间 |
| **风险影响** | 不还本，多少概率出 P0 / P1 事故 |
| **成本影响** | 不还本，每月多花多少（基础设施 / 维护人力） |

### 业务语言量化（必须有）

| 维度 | 量化 |
|------|------|
| 速度 | "目前新增一个相关功能需 6 周，还本后 3 周" |
| 风险 | "近 3 个月已发生 2 次 P1，影响 X 客户" |
| 成本 | "每月多支付 N 万云费用" |

> 没有量化的债 → 永远排不上优先级。

## WSJF / Cost of Delay 优先级

```
WSJF（Weighted Shortest Job First）= 
  (业务价值 + 时间紧迫度 + 风险 + 机会成本) / Job Size

业务价值 = 还本后每月节省的工时 / 收入提升
时间紧迫度 = 不还本 N 月后会怎样
风险 = 不还本带来的潜在故障概率 × 影响
机会成本 = 不还本阻塞了哪些新功能
Job Size = 还本预估工时（人月）
```

**排序：WSJF 高的先还。**

## 容量分配（20% 规则）

| 比例 | 用途 |
|------|------|
| 60-70% | 新功能 / 用户价值交付 |
| 10-20% | 技术债（含基础设施投资）|
| 10-15% | Bug 修复 |
| 5-10% | Spike / 探索 / 工具链 |

> 长期忽视技术债（占比 < 10%）→ 6-12 个月后速度断崖式下降。

**约定俗成**：每个 Sprint 至少 1-2 个技术债故事进入 Backlog。

## SLO（服务水平目标）守门

PM 应该和工程协商一套 SLO，违反时**自动触发还本**：

| SLO | 阈值 | 违反时动作 |
|-----|------|-----------|
| 可用性 | < 99.5% | 暂停新功能，全员做稳定性 |
| P95 延迟 | > 500ms | 性能投资 |
| 测试覆盖 | < 60% | 必须补测试再上 |
| 部署频率 | < 1次/周 | 投资 CI/CD |
| MTTR | > 1 小时 | 投资监控 |

## 季度技术债评审流程

```
T-2 周：
  工程团队整理技术债清单（每条带量化）
  PM + EM 共同打分 WSJF
  
T-1 周：
  联合评审会（PM、EM、技术 Lead、架构）
  - 排序 WSJF
  - 分组：本季度做 / 下季度做 / 暂不做
  - 分配下季度 20% 容量
  
T-0：
  把入选的技术债故事写进 Backlog
  设置 SLO 监控告警
  
T+季度末：
  复盘：还本后的实际收益（量化）
  对比预测 vs 实际
```

## 与产品功能的取舍话术

PM 常被问："为什么这个新功能不优先做？" — 用业务语言回答：

| 场景 | 推荐话术 |
|------|----------|
| 客户问 | "我们在改进底层平台，让未来所有功能（含您要的）能更快上线" |
| 销售问 | "这个底层投资能在 Q3 让我们交付能力 +50%，远超不做这个的新功能价值" |
| 老板问 | "不做这个，下季度的 5 个功能会变成 3 个；做了，下下季度的 5 个会变 8 个" |

## 反模式

- ❌ **工程自己决定，PM 不参与**：业务方向脱节
- ❌ **PM 一刀切不让做技术债**：复利积累，1 年后全员瘫痪
- ❌ **没有量化**：永远排不上优先级
- ❌ **没有 SLO 守门**：等到出 P0 才补，代价 10 倍
- ❌ **"今年做完技术债再做新功能"**：技术债永远做不完，要做的是持续还本
- ❌ **PM 不懂工程，全权交给 EM**：失去业务视角，工程做"工程师觉得有趣的"
