# pm-solution-decompose — 业务方案拆解工具箱

> 本 skill 被 `/pm-solution` 命令调用。

## 一、业务流程生成模板

### 主流程（Happy Path）标准动作序列

任何业务流程都能对齐到"入口 → 输入 → 处理 → 存储 → 反馈 → 出口"六段：

```mermaid
flowchart LR
  E[Entry 入口] --> I[Input 输入] --> P[Process 处理]
  P --> S[Store 存储] --> F[Feedback 反馈] --> X[Exit 出口]
```

对齐 checklist：
- **入口**：从哪个页面 / 什么触发 / 谁触发
- **输入**：需要什么数据 / 有几种输入方式
- **处理**：核心业务规则 / 是否调用外部服务 / 是否需要审批
- **存储**：写入哪些表 / 是否事务 / 是否幂等
- **反馈**：给用户展示什么 / 通知谁 / 埋点什么
- **出口**：下一个页面 / 后续动作

### 分支流程（合理分支）

至少要有以下三类：
1. **审批分支**（通过 / 拒绝 / 补充材料）
2. **数量分支**（单条 / 批量 / 部分成功）
3. **权限分支**（有权限 / 无权限 / 需升级）

### 异常流程（Unhappy Path）

必须覆盖 5 类：

| 类别 | 触发 | 系统处理 | 用户体验 |
|---|---|---|---|
| **网络异常** | 请求超时 / 断网 | 本地重试 3 次 → 保存草稿 | Toast + 保存草稿提示 |
| **权限不足** | 操作超出角色权限 | 拦截，不落库 | 权限说明 + 申请入口 |
| **数据校验** | 输入格式错 / 数据冲突 | 拒绝写入 | 字段级红字提示 |
| **并发冲突** | 多人同时改一条 | 乐观锁 → 提示冲突 | 展示差异 + 覆盖/合并选项 |
| **外部依赖** | 三方 API 不可用 | 降级方案（如短信兜底） | 静默降级 + 埋点 |

## 二、P0/P1/P2 分级规则

### 判定矩阵

用两个维度：**是否核心业务价值** × **是否本次交付**。

| \ | 本次必须交付 | 可以延后 |
|---|---|---|
| **核心价值** | **P0** | P1 |
| 非核心 | P1 | **P2** |

### P0 定义（缺了业务跑不通）
- [ ] 核心业务流程的每一步动作
- [ ] 上线合规必需（如个保法要求的隐私弹窗）
- [ ] 数据完整性必需（如幂等、事务）
- [ ] 关键角色的最低权限

### P1 定义（有更好、暂时可绕过）
- [ ] 提升效率但可用替代方案
- [ ] 部分角色的辅助功能
- [ ] 更好的用户体验
- [ ] 非关键场景的异常处理

### P2 定义（本次不做）
- [ ] 长尾场景
- [ ] 探索性功能
- [ ] 依赖尚未成熟的技术
- [ ] 未验证价值的假设

### 常见分级陷阱

| 陷阱 | 症状 | 修正 |
|---|---|---|
| P0 泛化 | 把所有需求都打 P0 | 每个 P0 必须回答"缺了会怎样" |
| P1 = 中优先级 | 用"中"糊弄 | P1 必须说明"绕过方案是什么" |
| P2 = 未来 | 变成"以后再说" | P2 必须说明"什么条件下重新评估" |

## 三、权限矩阵模板

### B 端 SaaS 常见角色

| 角色 | 典型职责 | 数据可见范围 |
|---|---|---|
| 系统管理员 | 配置全局参数 | 全租户 |
| 组织管理员 | 管理成员、权限组 | 单租户 |
| 部门负责人 | 审批、看部门数据 | 单部门 |
| 业务操作员 | 日常执行 | 自己创建的数据 |
| 审计 | 只读、日志 | 全租户只读 |
| 财务 | 对账、报表 | 单租户财务视图 |

### 权限矩阵 4 级

- ✅ 完整（增删改查）
- ✏️ 编辑（改，不能删）
- 👀 只读
- ❌ 无权限

### 矩阵检查 checklist
- [ ] 每个功能都被明确到"谁能做"
- [ ] 每个角色都被明确到"能做什么"
- [ ] 交叉项没有留空（留空 = 未定义 = 上线后会出事）
- [ ] 高危动作（删除、跨租户操作、导出）单独说明

## 四、依赖识别 checklist

### 内部依赖

| 类型 | 典型 | 需追问 |
|---|---|---|
| 数据 | 用户表、订单表 | 数据源是谁维护的？延迟多少？ |
| 服务 | 通知中心、账号中心 | SLA 多少？有 fallback 吗？ |
| 流程 | 审批链、财务核算 | 是否可绕过？ |
| 组织 | 需要客服培训、销售话术 | 培训周期？ |

### 外部依赖

| 类型 | 典型 | 关键指标 |
|---|---|---|
| 通信 | 短信 / 邮件 / IM Bot | QPS / 到达率 / 单价 |
| 支付 | 微信 / 支付宝 / Stripe | 到账时长 / 手续费 |
| 认证 | OAuth / SAML / 企微 / 飞书 | 稳定性 / 数据字段 |
| AI | OpenAI / Claude / 国内模型 | Token 单价 / 延迟 / 私有部署 |
| 地图 / 短链 / 存储 | 高德 / 腾讯云 COS | 用量单价 / 合规 |

每项依赖必须回答：
1. **用途**：为什么用？
2. **关键指标**：QPS / 延迟 / 单价 / 合规
3. **失败降级**：不可用时怎么办？
4. **替换成本**：换一家难度多大？

## 五、风险识别 checklist

### 5 类风险（缺一不可）

#### 1. 合规 / 法务
- [ ] 是否涉及个人信息（PII）？
- [ ] 是否涉及金融、医疗、政务等强监管？
- [ ] 数据是否需要本地化？
- [ ] 是否涉及跨境传输？
- [ ] 是否需要备案 / 认证（等保、SOC2）？

#### 2. 商业
- [ ] 是否影响现有付费用户体验？
- [ ] 是否给竞品送弹药？
- [ ] 客户流失概率？
- [ ] 定价与客户预算是否匹配？

#### 3. 交付
- [ ] 依赖的团队是否有档期？
- [ ] 是否需要新招人 / 新采购？
- [ ] 里程碑与预算是否匹配？
- [ ] 是否有"最后一公里"（培训、迁移、验收）？

#### 4. 组织
- [ ] 需要哪些跨部门决策？
- [ ] 谁最有可能反对？为什么？
- [ ] 老板是否已 buy-in？
- [ ] 一线执行团队是否理解 why？

#### 5. 技术风险（不深入，仅识别）
- [ ] 是否依赖新技术栈？
- [ ] 是否有性能天花板？
- [ ] 是否有数据一致性挑战？

（详细技术风险交给 /pm-tech-spec 或研发团队）

## 六、优先级冲突调停套路

当 PM 手动调整 P0/P1/P2 时，用以下四问检查：

1. 移动到 P0 的项，是否满足"缺了跑不通"？
2. 移到 P2 的项，是否满足"本次不上线不影响价值"？
3. 保留在 P1 的项，是否有"如果没做，用什么绕过"的说明？
4. 调整后 P0 项数量：C 端 ≤ 15 / B 端 ≤ 25，超出说明范围太大，建议拆版本。
