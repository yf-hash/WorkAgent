# pm-requirement-clarify — 需求澄清工具箱

> 本 skill 被 `/pm-clarify` 命令调用。不建议单独使用。

## 一、七要素识别 checklist

任何一份原始需求，必须能回答以下 7 个问题；无法回答的即为"缺失"，答案模糊的即为"歧义"。

| # | 要素 | 判定标准 | 示例（合格 / 不合格） |
|---|---|---|---|
| 1 | 业务目标 | 有可量化的成功指标 | ✅"月末对账时间从 4h → 30min" ❌"提升效率" |
| 2 | 用户是谁 | 角色 + 规模 + 决策权 | ✅"财务主管，全国 800 人，独立采购权" ❌"我们的用户" |
| 3 | 使用场景 | 时间 / 地点 / 情境 / 频率 | ✅"月末最后 3 天，办公室或家里，每人每月 1 次" ❌"日常使用" |
| 4 | 成功标准 | 可测量 + 有时间点 | ✅"3 个月内 70% 财务主管月度活跃" ❌"用户满意" |
| 5 | 边界范围 | 明确的做什么 vs 不做什么 | ✅"支持导入 Excel，不支持 PDF" ❌"支持常见格式" |
| 6 | 约束 | 合规 / 时间 / 预算 / 技术 | ✅"12/31 前上线，符合 GDPR" ❌"越快越好" |
| 7 | 排除项 | 明确的场景/角色/功能不覆盖 | ✅"不给外部审计使用" ❌"—"（空） |

## 二、B 端 SaaS 需求模板（默认）

用于 auto 模式给假设项打底。

```
【业务目标】{可量化指标}
【买单角色】{谁付钱}
【使用角色】{谁天天用}
【决策链】{IT / 业务 / 财务 / 合规 谁签字}
【集成】{需要对接的现有系统}
【数据隔离】{单租户 / 多租户 / 私有化}
【SLA】{可用性、恢复时间}
【合规】{等保、SOC2、GDPR、HIPAA、个保法}
【上线约束】{招投标周期、财年、审计窗口}
```

## 三、C 端需求模板

```
【业务目标】{DAU / 留存 / 付费转化 具体数字}
【用户画像】{核心用户 + 影响用户 + 决策者，往往同一个人}
【核心场景】{触发时刻 + 完成动作 + 情感状态}
【留存钩子】{什么让用户第二次回来}
【付费理由】{为什么值得付 X 元}
【竞品对照】{替代方案 + 差异点}
【首屏体验】{5 秒内看到什么}
```

## 四、内部工具需求模板

```
【被替代的现状】{现在用什么、几步、耗时多少}
【使用频率】{每天 / 每周 / 每月}
【依赖数据源】{Excel、内部 API、外部 API}
【权限层级】{只读 / 编辑 / 审批 / 管理}
【培训成本】{学 15 分钟就能上手 / 需要专项培训}
```

## 五、冲突检测规则库

自动扫描下列常见冲突模式：

| # | 冲突模式 | 触发关键词 A | 触发关键词 B | 严重度 |
|---|---|---|---|---|
| C1 | 快 vs 稳 | 快速上线 / MVP / 尽快 | 十万并发 / 高可用 / SLA 99.99% | 高 |
| C2 | 简单 vs 灵活 | 简单易用 / 一键 | 支持定制 / 复杂配置 | 中 |
| C3 | 免费 vs 高质量 | 免费 / 不收钱 | 专业级 / 企业级 / 高性能 | 高 |
| C4 | 隐私 vs 智能 | 隐私保护 / 数据不出域 | 大模型 / AI 分析 / 云端 | 高 |
| C5 | 自动 vs 可控 | 全自动 / 无需人工 | 每步都要审批 / 可控 | 中 |
| C6 | 广覆盖 vs 深功能 | 覆盖所有场景 | 深度垂直 | 中 |
| C7 | 短周期 vs 大范围 | 2 周上线 | 覆盖 5 个业务线 | 高 |
| C8 | 老板拍板 vs 用户导向 | 老板要 | 用户不想要 | 高（隐性） |

检测到冲突时，输出格式：

```
【冲突 C1】"快速上线"（原文位置：xxx）vs "支持十万并发"（xxx）
影响：MVP 通常无法满足高并发；建议决策：
  选项 A：先做单机版验证价值，并发放到 V2
  选项 B：延长上线时间到 3 个月做架构选型
  选项 C：明确用户规模上限（如 500 并发）
```

## 六、伪需求识别 checklist

真实业务目标往往藏在"表面需求"下面。识别 checklist：

| 表面需求特征 | 追问 | 真实需求可能是 |
|---|---|---|
| "加一个 X 按钮" | 用户按了这个按钮之后要干什么？ | 完成某个业务动作 |
| "支持 X 格式导出" | 导出后拿去做什么？ | 对接某个下游系统 |
| "增加一个 X 报表" | 谁看？看完做什么决定？ | 某个决策场景 |
| "首页加一个 X 模块" | 用户从这里跳去哪里最有价值？ | 某个转化路径 |
| "支持 X 语言" | X 语言用户占多少？愿意付费吗？ | 拓展某个市场 |
| "AI 化 / 智能化" | 具体哪一步用 AI？替代什么人工？ | 某个可量化的降本增效点 |

## 七、业务目标可量化校验

模糊表述 → 强制改写。

| 模糊 | 强制改写为 |
|---|---|
| "提升效率" | "把 X 动作从 Y 分钟降到 Z 分钟" |
| "改善体验" | "把 X 场景 NPS 从 Y 提到 Z" |
| "减少错误" | "把 X 错误率从 Y% 降到 Z%" |
| "增加收入" | "X 客群 ARPU 从 Y 提到 Z，或新客户数 +N" |
| "尽快上线" | "在 YYYY-MM-DD 前上线 X 功能" |
| "更多用户使用" | "3 个月内活跃用户数 +X%" |
| "客户满意" | "客户 NPS ≥ X 或续约率 ≥ Y%" |

## 八、待确认项分类矩阵

用于组织《需求澄清报告》的第 8 节。

```
业务问题（谁 / 值不值 / 什么优先）
  ├─ 目标衡量
  ├─ 优先级取舍
  └─ 阶段边界

用户场景问题（怎么用）
  ├─ 角色权限
  ├─ 频率与量级
  └─ 异常与失败路径

约束条件问题（能不能做 / 怎么做才合规）
  ├─ 合规与安全
  ├─ 集成与依赖
  └─ 时间与预算
```

## 十、反模式（禁止）

- ❌ auto 模式输出的假设没标【假设项】
- ❌ 冲突检测栏空缺（至少写"未检测到冲突"）
- ❌ 输出未回答七要素中的任一项
- ❌ 待确认项超过 20 条（说明本次范围太大，应先拆）
- ❌ 直接把用户原话搬到"业务目标"栏（必须用可量化改写）
