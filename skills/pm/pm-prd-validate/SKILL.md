# pm-prd-validate — PRD 四类校验工具箱

> 本 skill 被 `/prd --validate` 命令调用。

## 一、完整性校验规则库

### 每个功能必须回答的问题
- [ ] **功能目的**（为什么做，业务价值）
- [ ] **输入**（数据、触发方式、上游）
- [ ] **输出**（返回、写入、通知）
- [ ] **正常流程**（happy path，步骤级）
- [ ] **异常流程**（至少 3 类：数据异常 / 权限异常 / 依赖异常）
- [ ] **边界条件**（字段长度、数值范围、并发上限、频次）
- [ ] **权限**（谁能做，只读 / 编辑 / 审批）
- [ ] **失败处理**（重试策略、兜底方案、用户提示）
- [ ] **埋点**（关键动作事件定义）
- [ ] **验收标准**（GWT 或可测试断言）

### 全局章节必须包含
- [ ] 目标用户（含角色和规模）
- [ ] 业务目标（可量化）
- [ ] 非功能需求（性能、安全、兼容、可用性）
- [ ] 版本范围（P0/P1/P2）
- [ ] 上线约束（时间、依赖、合规）
- [ ] 风险点（含缓解方案）

### 缺失严重度分级
| 缺失项 | 严重度 |
|---|---|
| 异常流程、权限、验收标准 | 🔴 高（必须补） |
| 边界条件、失败处理、埋点 | 🟠 中（应该补） |
| 输入输出细节、上线约束 | 🟡 低（建议补） |

## 二、一致性校验规则库（需 `--input` 上游产物）

### 与《需求澄清报告》比对
| 检查项 | PRD 位置 | 澄清报告位置 | 判定 |
|---|---|---|---|
| 目标用户 | § 目标用户 | § 3. 目标用户 | 角色 / 规模 / 决策链一致 |
| 业务目标 | § 业务目标 | § 2. 业务目标 | 可量化指标一致 |
| 需求范围 | § 版本范围 | § 6. 需求范围 | P0 项对齐"本次包含" |
| 假设项 | § 风险与假设 | § 7. 假设项 | 未确认的假设必须出现 |

### 与《业务方案》比对
| 检查项 | 判定 |
|---|---|
| 主流程 | Mermaid 步骤序列一致 |
| P0/P1/P2 | 每一项都对得上 |
| 权限矩阵 | 角色 × 功能 一致 |
| 依赖清单 | 第三方依赖 & 内部依赖一致 |

### 与《原型底稿》比对
| 检查项 | 判定 |
|---|---|
| 页面清单 | PRD § 页面说明的每个引用都能在原型 JSON 找到 |
| 组件与字段 | 关键必填字段一致 |
| 状态覆盖 | PRD 描述的 4 状态与原型一致 |
| 跳转规则 | PRD 描述的跳转与原型 transitions 一致 |

### 冲突输出格式
```
【冲突 A1】
  PRD § "目标用户"："财务专员"
  澄清报告 § 3 § 目标用户："财务主管"
  影响：范围可能扩大，需重估 P0
  建议：以澄清报告为准；或若确认扩大，需回 M2 更新
```

## 三、歧义文本检测规则库

### 高频模糊词表（自动扫描）

**模糊程度词**：
```
优化 / 提升 / 改善 / 增强 / 更好 / 更快 / 更强
```

**模糊数量词**：
```
大量 / 少量 / 部分 / 若干 / 一些 / 多个 / 若干个
大部分 / 少部分 / 相当一部分
```

**模糊时间词**：
```
尽快 / 尽可能快 / 短时间内 / 未来 / 稍后 / 随时
一段时间 / 阶段性 / 逐步
```

**模糊程度词**（性能 / 体验）：
```
快 / 慢 / 好 / 差 / 稳定 / 流畅 / 顺滑
易用 / 好用 / 智能 / 智能化 / 灵活 / 通用
```

**模糊限定词**：
```
相关 / 相应 / 对应 / 合理 / 合适 / 适当 / 适度
基本 / 大概 / 大约 / 差不多
```

### 改写建议模板

| 原文 | 建议改写为 |
|---|---|
| "响应速度要快" | "接口 P95 响应时间 ≤ 500ms" |
| "支持大量数据" | "单次批量上限 10 万条" |
| "尽快加载" | "首屏 LCP ≤ 2.5s，可交互时间 ≤ 3.5s" |
| "用户体验优化" | "把 X 场景 NPS 从 Y 提到 Z" |
| "智能推荐" | "基于 X 特征 + Y 模型的推荐，Top10 CTR ≥ Z%" |
| "灵活配置" | "支持字段级配置：A、B、C 三个维度，管理员角色可改" |
| "合理的默认值" | "默认值 = 昨日 P50 值，可管理员改" |

### 扫描输出格式
```
【歧义 A1】"我们要优化用户体验"（§ 2. 业务目标）
  问题：优化 = 模糊程度词
  建议：改写为可量化指标，如"NPS 从 20 提到 40"或"任务完成率从 60% 提到 85%"
```

## 四、埋点完整性校验规则库

### 必须埋点的关键动作

| 动作类型 | 事件 | 属性 |
|---|---|---|
| 页面 PV | page_view | page_id, user_role, referrer |
| CTA 点击 | cta_click | cta_id, page_id, position |
| 表单提交（成功） | form_submit_success | form_id, duration_ms |
| 表单提交（失败） | form_submit_fail | form_id, error_code, error_msg |
| 支付 / 关键转化 | conversion_XX | amount, sku_id, channel |
| 搜索 | search_input | query, result_count |
| 筛选 | filter_apply | filter_id, filter_value |
| 空态触达 | empty_state_view | page_id, reason |
| 错误页触达 | error_page_view | page_id, error_type |
| 分享 / 邀请 | share_click | channel, entity_id |

### 埋点定义完整性
每个 event 必须包含：
- [ ] event_name（下划线命名，动词_名词）
- [ ] 触发时机（用户视角描述）
- [ ] 关键属性（≥ 2 个）
- [ ] 归属场景（page_id / feature_id）

### 缺失输出格式
```
【埋点缺失 A1】"用户点击'批量导出'按钮" (§ 3.2 批量导出功能)
  缺失：export_click 事件未定义
  建议 event：
    event_name: bulk_export_click
    trigger: 用户在列表页点击"批量导出"按钮
    properties: [export_type, filter_value, item_count, user_role]
```

## 六、校验通过标准

| 类别 | 通过标准 |
|---|---|
| 完整性 | 无 🔴 高严重度缺失 |
| 一致性 | 无冲突（有 --input 时） |
| 歧义文本 | 关键章节（目标 / 验收 / 边界）零模糊词 |
| 埋点 | 关键动作覆盖率 ≥ 90% |

四项全通过 → **总体：通过**
任一有 🔴 高严重度 → **总体：需重写**
其他 → **总体：有修改建议**
