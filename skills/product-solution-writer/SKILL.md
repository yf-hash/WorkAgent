# 产品解决方案写作知识库

> 单一文档类型 | 受众：行业客户 / 售前对接 | 密级：可公开 | 篇幅：30-60 页

---

## 核心原则

1. **从行业说起**：第一章必须建立行业背景，让客户感受"懂我"
2. **法规背书**：建设依据章节必须引用具体的法规、标准、政策（带文号）
3. **可视化为王**：必须含至少 3 张图：系统架构图 / 部署拓扑图 / 业务流程图
4. **量化收益**：建设收益章节用对比数字，避免"显著提升"类描述
5. **方案清单兜底**：最后一章给出可清点的方案组件清单

## 标准结构模板（七大章节）

```markdown

## 一、概述

（行业现状 / 业务挑战 / 监管要求）

（含整体架构图）

### 3.2 技术实现路径
（关键技术选型说明）

### 3.3 系统功能设计
#### 3.3.1 [主功能模块 1]
##### 3.3.1.1 [子功能 1]
##### 3.3.1.2 [子功能 2]

#### 3.3.2 [主功能模块 2]
...

## 四、部署模式
### 4.1 典型部署架构
（含部署拓扑图 / 网络结构图）

### 4.2 硬件配置建议
| 规模 | CPU | 内存 | 磁盘 | 网络 |
| 小型 | ... | ... | ... | ... |
| 中型 | ... | ... | ... | ... |
| 大型 | ... | ... | ... | ... |

## 五、方案优势
### 5.1 技术优势
（架构 / 性能 / 安全 / 可扩展）

### 5.2 服务优势
（实施 / 培训 / 售后 / SLA）

## 六、建设收益
### 6.1 业务收益（可量化）
| 指标 | 实施前 | 实施后 |

（通过认证 / 满足法规 / 审计达标）
```

## 行业定制要点

| 行业 | 必须涉及的合规标准 | 内容侧重 |
|------|------------------|---------|
| fintech | 等保 2.0 / 商密 / PCI-DSS / GDPR | 合规审计 / 风险控制 / 数据安全 |
| gov | 等保 2.0 / 国密 / 信创 / 政务云规范 | 政策符合性 / 国产化 / 可控性 |
| healthcare | HIPAA / 互联互通 / 等保 / 医疗数据规范 | 数据合规 / 互联互通 / 稳定性 |
| edu | 教育部数据规范 / 三级等保 | 易用性 / 扩展性 / 性价比 |
| mfg | 工控安全 / 等保 2.0 / 信创 | 系统集成 / 工厂部署 / ROI |
| retail | PCI-DSS / 个保法 / 电商运营规范 | 转化率 / 用户体验 / 数据洞察 |
| saas | SOC2 / ISO27001 / 个保法 / GDPR | 功能完整性 / 集成生态 / API |

## 质量要求

| 维度 | 标准 |
|------|------|
| 篇幅 | 30-60 页 |
| 图表 | 至少 5 张：架构 / 拓扑 / 流程 / 角色权限 / 业务场景 |
| 法规引用 | 至少 3 条带文号的标准 |
| 案例 | 至少 2 个同行业摘要案例 |
| 收益量化 | 至少 5 条对比数据 |

## 与相邻文档的区别

| 文档 | 范围 | 是否定制 |
|------|------|---------|
| **产品解决方案（本 Skill）** | 行业标准方案，可复用 | 按行业模板化 |
| 项目提案（proposal） | 针对特定客户 | 一次性定制 |
| 产品白皮书 | 单产品全方位介绍 | 不限行业 |
| 解决方案架构（solution-architecture） | 偏纯技术架构 | 偏架构师视角 |

发现是针对特定客户 → 用 `/proposal` 命令
发现只讲技术架构 → 用 `/solution-architecture` 命令
