# RFP / RFI 应答知识库

> 区别于 `bid-writer`（标书全流程编制）：本 Skill 专注**点对点的问询应答**，
> 客户给的不是招标文件而是结构化问题清单（Excel / Word / 在线问卷）。
> 区别于 `proposal-generator`（一对一方案撰写）：本 Skill 是**逐条作答**，不是写大块叙述。

---

## 一、应答模式四级法

| 模式 | 标签 | 应答原则 | 风险 |
|------|------|---------|------|
| **满足** | ✅ Comply | 直接 Yes + 一句话证据（功能名 / 文档章节 / 截图）| 低 |
| **部分满足** | ⚠️ Partial | Yes, with caveat — 说清楚"哪部分能 / 哪部分不能 / 缺口怎么补"| 中 |
| **替代方案** | 🔄 Alternative | "我方不直接支持 X，但通过 Y 达到相同业务效果" | 中（要让客户接受 Y）|
| **不满足** | ❌ Not Comply | 诚实承认 + 给出 roadmap 时间或工程估算 | 高（这条丢分但不能撒谎）|

**铁律**：
- 不能 100% 满足时，**绝对不写 ✅**。客户后期对照 PoC / 合同会扣分甚至索赔。
- "部分满足"必须明确边界，不能用"基本支持"这种含糊词搪塞。
- "替代方案"要量化成功率（"过往 3 个客户用此方案上线"）。

---

## 二、应答标准结构（每条问题）

```
【问题 ID】 客户原文
【应答模式】 ✅ / ⚠️ / 🔄 / ❌
【应答正文】
  - 一句话结论（Yes / Yes with X / Workaround / No）
  - 证据 1-3 条（功能模块 / 文档章节 / 配置示例 / 客户案例）
  - 风险或限制说明（如有）
【证据来源】 内部知识库链接 / 文档 / 截图编号
【负责人】 谁审核（产品 PM / 交付 / 法务 / 财务 / 安全）
【风险等级】 低 / 中 / 高
【对外发布】 是 / 否（部分内部话术不对外）
```

---

## 三、胜出主题（Winning Themes）

定义：贯穿整份应答的 3-5 个核心讯息，让客户读完每条问题后都强化同一个印象。

**典型胜出主题模板**：
1. **行业经验**：「我们在 [客户行业] 已交付 [N] 个项目，[3 个客户名]」
2. **合规背书**：「等保三级 + ISO 27001 + SOC 2 全部覆盖」
3. **本地化能力**：「全栈国产化适配 / 信创已认证 / 私有化部署支持离线运行」
4. **技术护城河**：「自研 [X 算法]，准确率 [Y]%，比业界平均高 [Z]pp」
5. **服务承诺**：「7×24 SLA + 4 小时响应 + 现场驻场可选」

**植入位置**：
- 每个关键问题（特别是评分项）的应答中，引用 1-2 个 Winning Theme
- 应答文件首页的 Executive Summary
- 关键章节的导语段

## 四、客户化语言转译

售前最大的坑是**用产品语言而不是客户语言**应答。

| 产品视角（错误） | 客户视角（正确） |
|----------------|----------------|
| "支持 RBAC 5 级权限" | "支持您组织的 5 级管理结构（总行 → 分行 → 支行 → 部门 → 个人）" |
| "采用 OIDC 集成" | "与您现有的 [客户 SSO 名] 单点登录系统对接" |
| "提供 REST API" | "支持与您 IT 系统现有 [具体系统名] 的集成" |
| "99.95% 可用性" | "全年宕机不超过 4.4 小时（区分非业务高峰排除）" |
| "多租户隔离" | "您各分行 / 子公司的数据严格隔离，互不可见" |

**原则**：用客户公开资料（年报 / 官网 / 招标文件 brief）里的术语，不用我方产品术语。

## 五、应答 KB 复用机制

成熟的售前团队 80% 的 RFP 应答都是历史复用。建立 KB 步骤：

```
Step 1: 历史 RFP 拆解
  把过往 5-10 份 RFP 应答按主题归类
  → 功能 / 安全 / 性能 / 集成 / 合规 / 部署 / 服务 / 商务

Step 2: 标准答案库
  每个常见问题维护 3 版应答：
    - 通用版（无行业属性）
    - 行业版（金融 / 政府 / 医疗 / 制造）
    - 客户版（针对特定大客户的定制版本）

Step 3: 检索匹配
  收到新 RFP → 按问题向量化匹配历史 KB → 优先复用 → 再做行业化调整

Step 4: 持续迭代
  每份新 RFP 应答完后回流 KB
  失败案例（lost deal）的应答打"⚠️ 已被对手击败"标签
```

## 六、分工矩阵（谁答哪类）

| 问题类别 | 负责人 | 审核人 |
|---------|--------|--------|
| 产品功能 / 业务流程 | 产品 PM | 产品总监 |
| 技术架构 / 集成方案 | 售前架构师 | 研发负责人 |
| 安全 / 合规 | 安全工程师 | CISO / 合规官 |
| 性能 / SLA | 运维负责人 | 售前架构师 |
| 商务 / 报价 / 服务 | 销售 | 销售总监 |
| 法律 / 合同条款 | 法务 | 法务总监 |
| 实施 / 交付 / 培训 | 交付经理 | 交付总监 |

**协作 SOP**：
- T-15 天：拆解 RFP → 分配负责人 → 设定 deadline
- T-10 天：第一轮应答（70% 完成）
- T-7 天：交叉评审 + 不一致项核对
- T-5 天：法务 + 财务终审
- T-3 天：客户化语言转译 + Winning Themes 植入
- T-1 天：版式打包 + 提交清单核对

## 七、风险措辞红线

**绝对不能写**：
- "100% 满足所有需求"（除非对所有需求都已 PoC 验证）
- "完全兼容所有 X 系统"（应改为"经验证兼容 [具体系统名清单]"）
- "无任何停机"（应改为"计划停机不超过 X 小时 / 年，提前 N 天通知"）
- "永久免费升级"（应改为"质保期内免费，质保后按服务合同"）

**风险措辞替换表**：

| ❌ 原文 | ✅ 替换 |
|--------|--------|
| 行业第一 | 业界领先（除非有具体数据来源）|
| 唯一支持 | 业内少数支持（除非有第三方报告引用）|
| 任何场景 | 已验证场景包括 [清单] |
| 完全兼容 | 已通过兼容性测试的清单：[X / Y / Z] |
| 实时 | P95 响应 <[N] 毫秒 |

## 八、应答评审清单（提交前必查）

```
□ 一致性
  □ 同类问题应答口径一致（不能这条说支持那条说不支持）
  □ 数据指标一致（性能 / SLA / 资质 全文同一数字）
  □ 客户名 / 项目名 / 产品名 全文一致

□ 完整性
  □ 所有问题已应答（无空白）
  □ 必填项（资质证书 / 客户证明 / 法定声明）已附

□ 风险
  □ 无 100% / 完全 / 永久 等绝对化表述
  □ 部分满足项已注明边界
  □ 不满足项有时间表或替代方案

□ 客户化
  □ 已用客户行业术语
  □ 已植入 3-5 个 Winning Themes
  □ 已引用客户行业相关案例

□ 格式
  □ 文件命名规范：[公司名]_[客户名]_[项目名]_应答_v[版本]_[日期].xlsx
  □ 已附目录 + 索引
  □ Excel 公式 / 图片 / 链接全部检查可用
```

## 九、与其他 Skill 的边界

| 选择 | 用前者 | 用后者 |
|------|-------|-------|
| `rfp-response` vs `bid-writer` | 客户给的是问题清单（Excel/Word）逐条作答 | 客户给的是招标文件，要做完整标书 |
| `rfp-response` vs `proposal-generator` | 逐条问答风格 | 大块叙述方案 |
| `rfp-response` vs `security-questionnaire` | 综合 RFP 含部分安全问题 | 纯安全问卷（200+ 条 VSQ）|
| `rfp-response` vs `gap-analysis` | 客户问 → 我方答 | 客户需求清单 vs 产品能力 主动映射 |
