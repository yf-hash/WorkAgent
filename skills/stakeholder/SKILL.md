# Stakeholder Management — 干系人管理知识库

把"协调一堆人"从凭感觉变成可识别、可分类、可施策的方法论。

---

# 一、干系人管理的"三个为什么"

```
1. 为什么要管干系人？
   → 项目失败的 70% 原因不是技术，是协作 / 沟通 / 政治
   
2. 为什么不是所有人一视同仁？
   → 时间和精力有限，必须按 Power-Interest 排序
   
3. 为什么坏消息要早说？
   → 越早说越多选择，越晚说越被动
```

---

# 二、Power-Interest 矩阵

```
                    Interest 低              Interest 高
                    ────────────────────    ────────────────────
Power 高           │ Keep Satisfied      │ Manage Closely     │
                   │                     │                     │
                   │ 不打扰但保持沟通     │ 深度协作            │
                   ────────────────────  ────────────────────
Power 低           │ Monitor             │ Keep Informed       │
                   │                     │                     │
                   │ 监测变化            │ 定期同步            │
                   │                     │                     │
                   ────────────────────  ────────────────────
```

| 象限 | 沟通频次 | 沟通内容 |
|------|---------|---------|
| Manage Closely | 每周 / 关键节点 | 决策点 + 风险 + 资源 |
| Keep Satisfied | 双周 / 月度 | 关键数字 + 风险摘要 |
| Keep Informed | 月度 | 进度 + 影响他们的事 |
| Monitor | 季度 / 按需 | 重大变化通知 |

**Power**：决定/否决项目的能力
**Interest**：受项目影响 + 关心程度

# 三、干系人角色类型

```
Sponsor（发起人）       提供资源，最终为成败负责
Champion（拥护者）      内部支持者，帮你说服别人
Decider（决策者）       拍板权
Influencer（影响者）    影响决策但不直接拍板
Approver（审批者）      流程关卡（法务 / 合规 / 安全）
Blocker（阻碍者）       潜在反对者
User（最终用户）        最终使用产品的人
```

**关键洞察**：
- Sponsor ≠ Decider（资源方不一定决策）
- Decider ≠ Champion（决策者可能不主动）
- 必须识别 Blocker 并提前沟通

# 四、RACI 责任矩阵

```
R - Responsible (执行者)：实际做事的人
A - Accountable (负责者)：拍板的人，承担最终责任
C - Consulted (被咨询)：双向沟通，意见会被参考
I - Informed (被告知)：单向通知，知情即可
```

## 4.1 RACI 设计原则

```
1. 每个任务必须有且仅有 1 个 A（避免决策模糊）
2. R 可以多人（多人执行）
3. C 不要太多（咨询人多决策慢）
4. I 比 C 多（多告知没坏处）
```

## 4.2 RACI 模板

```
| 任务         | PM | Eng | Design | Sales | CEO |
|-------------|----|----|--------|-------|-----|
| 需求确认     | R/A| C  | C      | C     | I   |
| 技术方案     | A  | R  | C      | I     | I   |
| 设计稿       | A  | C  | R      | I     | I   |
| 上线决策     | R/A| R  | I      | I     | I   |
| 战略方向     | C  | I  | I      | I     | R/A |
```

# 五、沟通节奏设计

## 5.1 按受众分层

| 受众 | 关心什么 | 不关心什么 | 推荐内容 |
|------|---------|-----------|---------|
| CEO / 高管 | 数字 / 战略 / 风险 | 技术细节 | 1 页摘要 + 决策点 |
| 工程 Lead | 技术 / 工时 / 优先级 | 销售话术 | 详细方案 + 估算 |
| 销售 | 卖点 / 案例 / 竞品 | 实现细节 | 卖点卡 + Demo |
| 客服 | 用户影响 / 培训 | 战略 | 培训材料 + FAQ |
| 设计 | 用户旅程 / 体验 | 商业模型 | 用户故事 + 反馈 |
| 数据 | 埋点 / 指标 / 假设 | 视觉 | 指标方案 + Schema |

## 5.2 跨团队会议节奏

```
项目期：
  W0：Kick-off（所有人）
  Wn：每周站会（Manage Closely）
  双周：跨团队同步（Keep Informed）
  月度：高管汇报（Keep Satisfied）
  关键节点：评审会（按需）

非项目期：
  双周：1on1（直接 Stakeholder）
  月度：跨部门会
  季度：战略对齐
```

# 六、向上管理（Managing Up）

## 6.1 高管最讨厌的汇报方式

```
❌ 长篇技术细节
❌ 没有结论先讲过程
❌ 抛问题不抛方案
❌ 等到火烧眉毛才说
❌ 模糊措辞 "可能" "也许"
```

## 6.2 高管喜欢的汇报方式

```
✅ 30 秒讲清结论 + 决策点
✅ 用数字而非形容词
✅ 风险 + 你的应对建议
✅ 提前同步坏消息（不被动）
✅ 给出选择而非问"怎么办"
```

## 6.3 黄金 30 分钟模板

```
00:00 - 00:30  一句话核心结论
00:30 - 02:30  关键数字
02:30 - 07:30  风险 + 应对
07:30 - 17:30  决策点（你需要的）
17:30 - 22:30  资源 / 支持 诉求
22:30 - 30:00  下次汇报安排
```

# 七、Champion 与 Blocker 转化

## 7.1 Champion 培养

```
1. 找出"项目对他有什么个人价值"
2. 让他在管理层会议为你背书
3. 让他先用到 / 先看到（早期 Beta）
4. 公开认可他的贡献
```

## 7.2 Blocker 转化

```
1. 弄清反对原因（深度访谈，不预设）
2. 共同利益识别（项目能帮他什么）
3. 让他参与决策（从"被动反对"到"共同决策"）
4. 不能转化时，至少做到中立（不积极反对）
5. 极端情况：升级到双方共同上级裁决
```

# 八、坏消息传递 SOP

## 8.1 越早越好

```
项目偏离 5%：私下通知核心 Stakeholder
偏离 10%：写明决策选项给 Decider
偏离 20%：召开正式 Risk Review
偏离 > 30%：升级到 Sponsor / 高管层
```

## 8.2 坏消息四要素

```
1. 状态：发生了什么（事实，不评价）
2. 原因：为什么会这样（不甩锅）
3. 影响：会产生什么后果（量化）
4. 方案：你打算怎么办（含选项）
```

## 8.3 坏消息话术模板

```
"我有一个需要你了解的情况。

发生：[简要事实]
原因：[根因，不甩锅]
影响：[对项目 / 商业 / 用户]
建议：
  - 选项 A：[方案]，代价是 X
  - 选项 B：[方案]，代价是 Y
  - 选项 C：[方案]，代价是 Z

我推荐 [X]，因为 [理由]。
需要你 [日期] 前的决策。"
```

# 九、升级流程（Escalation Path）

## 9.1 何时升级

```
✅ 跨部门冲突，平级解决不了
✅ 关键风险即将发生，需要更高层资源
✅ 决策超出自己权限
✅ 重大方向偏离需要 Sponsor 拍板
```

## 9.2 升级前自查

```
□ 已尝试平级沟通（≥ 2 次）
□ 已记录沟通过程
□ 有具体的决策选项
□ 不是甩锅而是寻求帮助
□ 给被升级方一个 reasonable 的 SLA
```

## 9.3 升级礼仪

```
1. 先告知对方"我打算升级"，给他自我修正机会
2. 升级时同时抄送对方（透明）
3. 表述事实 + 影响 + 选项，不带情绪
4. 升级后双方关系修复（不要破坏长期合作）
```

# 十、外部干系人

## 10.1 客户管理

```
- 大客户：定期 Business Review（季度 / 年度）
- 早期客户：私聊群 + 优先回应
- 试用客户：Onboarding + 定期 Check-in
- 流失客户：Win-back 调研
```

## 10.2 监管 / 合规

```
- 提前接入：项目立项时识别合规要求
- 咨询而非通知：让法务参与决策而非阻拦
- 留痕：所有合规审议留档
```
