# A/B Test — A/B 实验方法论知识库

把 A/B 测试从"凭感觉看哪个数据高"变成可决策的科学流程。

---

# 一、A/B 实验的"四个为什么"

```
1. 为什么做这个实验？      → 假设 + 商业价值
2. 为什么主指标是它？      → OEC 选择逻辑
3. 为什么这个样本量够？    → Power Analysis
4. 为什么相信这个结论？    → 显著性 + 护栏 + 异常排查
```

---

# 二、实验假设结构化

## 2.1 假设三件套

```
If    [变更/Treatment]
For   [目标用户群]
Then  [主指标] will [方向] by [MDE]
Because [背后用户/业务洞察]
```

例：
```
If    我们将注册按钮文案从"立即注册"改为"免费试用 14 天"
For   首页访问的非注册用户
Then  注册转化率将从 12% 提升到 ≥ 13.5%（+1.5pp）
Because 用户进入决策时痛点是"会不会浪费时间"，"免费试用"消除
        承诺感，"14 天"给出明确退出
```

## 2.2 假设质量自检

```
✅ 有具体的变更（不是模糊"优化")
✅ 有限定的用户群（不是"所有人"）
✅ 有可衡量的指标和方向
✅ 有可证伪的预期幅度（MDE）
✅ 有用户/业务层面的因果机制（Why）
```

---

# 三、主指标（OEC）选择

OEC = Overall Evaluation Criterion

```
✅ 与北极星指标方向一致
✅ 实验周期内可观测（不能等 6 个月才看到）
✅ 对实验变更敏感
✅ 不易被异常/Bot/外部因素污染
✅ 可量化、清晰口径定义

❌ 多个主指标（决策悖论）
❌ 滞后指标作为主指标（如年度续约率）
❌ 自定义复合指标（解释性差）
```

常见 OEC 选择：
| 实验类型 | 推荐 OEC |
|---------|---------|
| 注册流程 | 注册完成率 |
| 引导流程 | D1/D7 激活率 |
| 推荐算法 | 点击率（短期）+ 留存（长期）|
| 定价改版 | 付费转化 + ARPU |
| 性能优化 | P95 响应时间 + 用户感知操作完成率 |

# 四、护栏指标（Guardrails）

防止主指标提升但损害其他维度。至少 3 类：

```
1. 用户体验类
   - 页面加载 P95
   - JS Error 率
   - Crash 率

2. 业务底线类
   - 主漏斗其他步骤转化率
   - 客单价
   - 退款率/客诉率

3. 平台健康类
   - 数据库 QPS
   - 服务延迟
   - 收入总量（防止流量倾斜）
```

护栏指标的判定：
- 显著变差且超过预设阈值 → 即使主指标赢也不上线
- 不显著但临界 → 风险评估后决策

# 五、分流策略

## 5.1 实验粒度（Unit of Randomization）

```
✅ user_id（推荐，持久化、可追踪）
⚠️ session_id（同用户多次访问可能进不同组，损失体验）
⚠️ device_id（多端用户可能不一致）
❌ 请求级（cookie 无、严重污染）
```

## 5.2 多实验并行：分层正交

```
Layer 1（互斥）        ┌─ Exp A1（推荐算法）
                       └─ Exp A2（推荐算法）

Layer 2（与上层正交）   ┌─ Exp B1（引导流程）
                       └─ Exp B2（引导流程）

Layer 3（与上层正交）   ┌─ Exp C1（按钮文案）
                       └─ Exp C2（按钮文案）

每个用户：在每一层独立分桶
```

适用：实验之间预期无显著交互，希望最大化流量利用。

## 5.3 互斥层（Holdout / 独占）

适用：
- 重大改版（避免叠加效应）
- 长期 Holdout 用于估算累积价值

# 六、样本量估算（Power Analysis）

## 6.1 双比例 z 检验公式

```
n_per_group = (Z_α/2 + Z_β)² × [p1(1-p1) + p2(1-p2)] / (p1 - p2)²

参数：
  Z_α/2  = 1.96（α = 0.05，双尾）
  Z_β    = 0.84（power = 0.8）
  p1     = baseline（如 0.12）
  p2     = baseline + MDE（如 0.135）
```

## 6.2 估算工具

```
- Evan Miller A/B Calculator: evanmiller.org/ab-testing/
- Optimizely Sample Size Calculator
- PostHog 内置计算器
- statsmodels.stats.power.NormalIndPower (Python)
```

## 6.3 时长估算

```
最短时长 = max(
  样本量 / 日均流量,
  覆盖业务周期（至少 1 个完整周）,
  覆盖用户行为周期（如订阅产品 ≥ 14 天）
)
```

## 6.4 多重比较校正

```
同时跑 K 个实验/指标：
  Bonferroni: α' = α / K（保守）
  FDR (Benjamini-Hochberg)：按 p 值排序后调整（推荐）
```

# 七、显著性检验

## 7.1 频率派（最常用）

```
- 双比例 z 检验（比例类指标）
- 双样本 t 检验（连续指标）
- Mann-Whitney U（非正态分布连续指标）
- 卡方检验（多类别 / SRM）
```

## 7.2 Bayes 派

```
P(B 优于 A | 数据) = ?
特点：
  ✅ 可解读（"B 有 95% 概率比 A 好"）
  ✅ 不需要预设样本量，可随时停
  ⚠️ 需要先验分布（实践中常用 Beta(1,1)）
工具：
  - GrowthBook 默认采用
  - PostHog 也支持
```

## 7.3 频率派 vs Bayes 派选择

| 场景 | 推荐 |
|------|------|
| 监管/学术报告 | 频率派 |
| 团队懂统计 | 频率派 |
| 快速决策 / 多次小实验 | Bayes |
| 不希望陷入 Peeking 陷阱 | Bayes（但用 Always Valid p-value） |

# 八、典型陷阱

## 8.1 SRM (Sample Ratio Mismatch)

预期 50/50 但实际 49/51 → 用 χ² 检验：

```
H₀: 分流比例 = 预期
若 p < 0.001 → 怀疑分流逻辑/数据丢失
```

常见 SRM 原因：
- A/B 重定向逻辑有 Bug（A 组首屏流失更多）
- Bot 流量分配不均
- 数据丢失/事件未上报
- Sticky bucketing 失效

## 8.2 Peeking / 偷看

每天看一次 p 值，看到 < 0.05 就停 → 实际 α 远高于 0.05

防范：
- 提前定好样本量，到点才看
- Always Valid p-value（mSPRT）
- Bayes 法（设决策门槛而非 p）

## 8.3 辛普森悖论

整体显著但分群方向相反 → 流量结构不对称

防范：
- 关键维度分群分析（设备/地区/老新用户）
- 确认分流均匀

## 8.4 抢跑/停车（Early Stopping）

- 见好就收 → 高估效果
- 见差就停 → 低估效果

防范：预设决策矩阵，不让人临时改主意。

## 8.5 网络效应污染

社交/双边产品：A 组用户行为影响 B 组（点赞/评论可见）

防范：
- 分桶到群组而非用户（cluster randomization）
- Holdout 长期监测累积效应

# 九、决策矩阵

```
| 主指标变化 | 护栏检查 | 决策                            |
|------------|----------|---------------------------------|
| 显著上升   | 通过     | ✅ 全量发布                      |
| 显著上升   | 部分变差 | ⚠️ 商讨权衡 → 加 LRU 缓存等优化  |
| 不显著     | 通过     | ⏸️ 加大样本 或 改方案再测         |
| 不显著     | 部分变差 | ⏸️ 不上线，分析变差原因          |
| 显著下降   | —        | ❌ 立即下线 + 复盘原因           |
```
