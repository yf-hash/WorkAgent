# Prd Quality Check — PRD 质量自检

> 单一职责：对已有 PRD 文档做质量评分与改进建议。
> 不做：写新 PRD（→ `prd-standard` / `prd-spec-first` / `prd-lite` / `prd-proto`）

> 评分基线来源：prd-mcp-server（https://github.com/saml1211/prd-mcp-server）

## 5 维度评分

| 维度 | 权重 | 检查项 |
|------|------|--------|
| 完整性 | 30% | 包含背景/目标/用户/功能/指标/风险六要素 |
| 可测性 | 25% | 验收标准使用 Given/When/Then 格式 |
| 可量化 | 20% | 成功指标有具体数值，非模糊描述 |
| 边界明确 | 15% | 有"不在范围"章节，排除项有理由 |
| 数据支撑 | 10% | 背景描述有数据来源，非主观判断 |

**评分标准**：优秀（90-100）/ 良好（75-89）/ 待改进（60-74）/ 不合格（< 60）

## 自检清单

```
完整性（30%）
- [ ] 有明确的背景/问题陈述（附数据或用户反馈）
- [ ] 有可量化的成功标准（非模糊描述）
- [ ] 有目标用户画像（至少一个主要角色）
- [ ] 有功能规格（用户故事/验收标准）
- [ ] 有指标体系（北极星/核心/护栏指标）
- [ ] 有风险评估（技术风险/业务风险）

可测性（25%）
- [ ] 验收标准使用 Given/When/Then 格式
- [ ] 每个用户故事有至少一个正常路径 AC
- [ ] 每个用户故事有至少一个异常路径 AC
- [ ] 边界条件已覆盖（最大值/空值/并发）

可量化（20%）
- [ ] 成功指标有具体数值（如"从 18% 提升到 30%"）
- [ ] 时间范围明确（如"发布后 30 天内"）
- [ ] 性能需求有数字（如"P95 < 500ms"）

边界明确（15%）
- [ ] 有"不在范围"章节
- [ ] 排除项有说明理由
- [ ] 依赖项和前置条件已识别

数据支撑（10%）
- [ ] 背景描述有数据来源（非主观判断）
- [ ] 竞品对比有具体依据
- [ ] 用户反馈有真实案例
```

## 常见低分问题与修复

```
❌ 验收标准："系统应该支持多种登录方式"
✅ 修复：Given 用户在登录页，When 点击"微信登录"，
        Then 弹出微信授权页面，授权成功后自动登录

❌ 成功指标："提升用户满意度"
✅ 修复："NPS 从 32 提升到 45，发布后 60 天内"

❌ 缺少不在范围："本次实现登录功能"
✅ 修复："不在范围：单点登录（SSO）、SAML/LDAP 集成，留待企业版本实现"

❌ 功能描述无边界条件
✅ 补充：最大限制/并发处理/权限限制/网络异常
```

## 输出格式

```markdown
## PRD 评估报告

**总分**：[X]/100  **等级**：[优秀 / 良好 / 待改进 / 不合格]

### 各维度得分
| 维度 | 得分 | 权重得分 |
|------|------|---------|
| 完整性 | X/100 | X/30 |
| 可测性 | X/100 | X/25 |
| 可量化 | X/100 | X/20 |
| 边界明确 | X/100 | X/15 |
| 数据支撑 | X/100 | X/10 |

### 通过项
✅ [项 1]
✅ [项 2]

### 待改进项（按优先级）
1. ❌ [问题描述] → 建议：[具体修复方向 + 示例]
2. ⚠️ [问题描述] → 建议：[具体修复方向]

### 你希望我帮你：
A. 直接补充/修改薄弱的章节
B. 对整个文档进行全面重写
C. 只给出改进建议，你自己来修改
```
