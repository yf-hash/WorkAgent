# Build vs Buy Skill — 决策框架

## 核心原则

**不要凭直觉，结构化打分。** Build 不一定便宜，Buy 不一定快。每个项目都不同。

```
决策 = 战略价值（核心 vs 外围） × 时间窗口 × TCO × 风险
```

## 三步法

### 第 1 步：分类（这是什么级别的决策）

| 决策类别 | 默认偏向 | 例子 |
|---------|----------|------|
| **核心差异化能力** | Build | 客户对你产品的核心期待来自这块 |
| **基础设施 / 通用能力** | Buy | 没人因此选你或不选你 |
| **合规 / 安全 / 法务** | Buy 通常更稳 | 等保、SOC2 工具 |
| **客户专属定制** | Customize | 客户付钱要的非标 |
| **战略选项 / 未来杠杆** | Build 或 Hybrid | 现在不重要但未来可能成核心 |

### 第 2 步：维度打分（1-5）

| 维度 | 解释 | Build 得分 | Buy 得分 |
|------|------|-----------|----------|
| **战略价值** | 这件事和我们差异化关系大吗？| 越高越倾向 Build | 越低越倾向 Buy |
| **时间窗口** | 多久必须有结果？| 慢但灵活 | 快但锁定 |
| **总拥有成本（TCO）** | 3 年总成本 | 含人工 + 基础设施 + 维护 | 含订阅 + 集成 + 切换 |
| **控制力 / 灵活性** | 想多大程度定制？| 完全可控 | 受 vendor 限制 |
| **风险敞口** | 失败 / 切换代价多大？| 团队风险 | Vendor 锁定风险 |
| **机会成本** | 团队做这件事少做什么？| 高（占用研发）| 低 |
| **合规 / 安全** | 谁更容易过审计？| 视团队能力 | 通常已有合规证书 |

### 第 3 步：TCO 三年模型

```
Build TCO（3 年）：
  研发人工成本（初期 N 人月 + 持续 0.5N 人月维护）
+ 基础设施成本（云 / 服务器 / 监控）
+ 机会成本（这些工程师如果做其他事的价值）
+ 风险溢价（延期概率 × 延期代价）

Buy TCO（3 年）：
  订阅 / License 成本（每年 × 3）
+ 集成成本（一次性 + 升级）
+ 培训成本
+ 切换成本（如果 vendor 失败 / 涨价 / 关停）
+ vendor 风险溢价（生死 / 被收购 / 价格突变）
```

## 决策矩阵

```
              战略价值高              战略价值低
            ┌─────────────────┬─────────────────┐
  时间紧迫  │  Hybrid          │  Buy             │
            │  Buy 临时 + Build │  Buy（决定！）   │
            │  长期            │                  │
            ├─────────────────┼─────────────────┤
  时间宽裕  │  Build           │  Build / Buy 都行 │
            │  （决定！）       │  按 TCO 决定      │
            └─────────────────┴─────────────────┘
```

## 第三方供应商评估清单

如果决定 Buy，对每个候选 Vendor 评估：

| 维度 | 检查项 |
|------|--------|
| **产品能力** | 是否覆盖核心需求 90%+ |
| **本地化** | 中文 / 本地化部署 / 本地数据中心 |
| **客户基础** | 同行业有多少头部客户在用 |
| **财务健康** | 是否盈利 / 融资轮次 / 估值 / Burn Rate |
| **路线图对齐** | 我们想要的功能他们 12 个月内会出吗 |
| **集成能力** | API / Webhook / SSO / SCIM 完整度 |
| **合规** | 等保 / SOC2 / ISO27001 / GDPR 证书 |
| **SLA** | 可用性承诺 / 响应时间 / Service Credit |
| **数据归属** | 数据是谁的，离场怎么导出 |
| **退出策略** | 终止合约的预先通知期、数据迁移支持 |
| **价格透明度** | 标准报价 / 阶梯折扣 / Multi-Year 优惠 |
| **支持** | 中文支持 / 工时区 / 升级响应 |

## Hybrid 模式（最常被忽略）

**Buy + Customize**：
- 买基础平台
- 自研客户面 / 差异化层
- 例子：买 Auth0 做身份，自研 RBAC 业务规则

**Buy 临时 + Build 长期**：
- 短期买 SaaS 抢市场
- 团队同时孵化自研版本，2-3 年迁移
- 例子：MVP 用 OpenAI，6 个月后切私有部署

**Build 核心 + Buy 周边**：
- 核心引擎自研
- 周边工具用 SaaS（监控 / 日志 / 通知 / 调度）

## 反模式

- ❌ **拍脑袋"我们能做"就 Build**：低估持续维护成本
- ❌ **"开源免费"就 Buy**：忽略集成 / 运维 / 安全审计成本
- ❌ **只看初期成本**：3 年 TCO 才是真账
- ❌ **不考虑机会成本**：研发团队做这件事少做了什么？
- ❌ **忽略退出策略**：买了不能下贼船，3 年后被锁死涨价
