# PM Decision & Communication Frameworks — 优先级排序 + 向上沟通

> **单一职责**：PM 侧的"取舍决策 + 结论传达"框架。两块内容配套使用：先用第一部分决定"该做什么"，再用第二部分把决策"讲清楚"。
> **不做**：需求发现（→ `pm-discovery-frameworks`）、路线图（→ `product-roadmap`）、指标框架（→ `pm-metrics-frameworks`）。

---

# 一、优先级排序框架

## 框架速查

| 框架 | 公式/说明 | 适用场景 |
|------|---------|---------|
| RICE | (Reach × Impact × Confidence) ÷ Effort | 多需求横向比较 |
| MoSCoW | Must / Should / Could / Won't | MVP 范围界定 |
| ICE | Impact × Confidence × Ease | 快速优先级 |
| Kano | 必备 / 期望 / 惊喜 / 反向 / 无差异 | 功能价值分类 |

## RICE 详解

```
RICE Score = (Reach × Impact × Confidence) ÷ Effort

- Reach（覆盖）：N 名用户/月
- Impact（影响）：3=巨大 / 2=高 / 1=中 / 0.5=低 / 0.25=极小
- Confidence（置信度）：100% / 80% / 50%（< 50% 应先做 PoC）
- Effort（工作量）：人月

示例：
| 需求 | Reach | Impact | Confidence | Effort | RICE |
|------|-------|--------|-----------|--------|------|
| 评论功能 | 5000 | 2 | 80% | 4 | 2000 |
| Onboarding 改版 | 8000 | 1 | 100% | 2 | 4000 ← 优先做 |
```

## MoSCoW 详解

```
Must Have（必备）：缺了产品就垮，零容忍
Should Have（重要）：缺了体验受损但能用
Could Have（锦上添花）：有时间就做
Won't Have（不做）：明确排除，写入 PRD §5.2

使用要点：
- Must 占比 < 60%，否则就是没做取舍
- 每个 Won't 都要说清"为什么本期不做"
- MoSCoW 是阶段共识，不是永久禁令
```

## ICE 详解

```
ICE Score = Impact × Confidence × Ease（每项 1-10 分）

适合：快速会议、灵感排序、增长实验
缺点：精度不如 RICE，不适合大投入决策
```

## Kano 详解

```
五类功能：
- 必备型（Must-be）：缺了不满意，有了也不会特别满意
  例：登录、支付安全
- 期望型（One-dimensional）：越多越好，与满意度线性相关
  例：响应速度、价格优惠
- 兴奋型（Attractive）：超预期，惊喜
  例：意外彩蛋、AI 智能补全
- 反向型（Reverse）：有了反而不满意
  例：过度推荐、强制升级
- 无差异型（Indifferent）：用户不关心
  例：无人用的高级设置

使用要点：
- 通过 Kano 问卷量化（功能存在/不存在 两个问题）
- 必备型不做就完，期望型决定竞争力，兴奋型创造惊喜
- 兴奋型会随时间退化为必备型（智能手机摄像头）
```

## 框架组合使用

```
场景 → 框架选择：
- 需求池有 50+ 个候选 → RICE（量化排序）
- MVP 范围讨论会 → MoSCoW（快速达成共识）
- 增长实验排序 → ICE（轻量快速）
- 大版本功能价值评估 → Kano（区分类型）
```

# 二、向上管理与汇报框架

> **一句话原则**：决策做完不算完，讲清楚才算完。汇报的核心不是"我做了什么"，而是"你需要知道什么 / 需要你做什么"。

## 四大原则（BLUF）

```
1. 结论先行（Bottom-line up front, BLUF）
   开头一句话给结论，再展开论证
   ❌ "经过一周的工作，团队完成了..."
   ✅ "本周关键结论：D7 留存从 23% 提升到 31%，超目标 6 pp。"

2. 数据支撑（用指标说话，不用感受）
   ❌ "用户反响很好"
   ✅ "NPS 从 41 提升到 53，30 天内"

3. 推荐方案（给选项而非问题）
   ❌ "用户付费转化低了 / 怎么办？"
   ✅ "用户付费转化降至 1.8%，建议 A: 调整定价 / B: 加引导，推荐 A"

4. 风险透明（提前暴露，带缓解方案）
   ❌ "可能会延期"（暴露后无方案）
   ✅ "T+5 上线有风险（依赖 X 服务），缓解：备选 Y 路径，回滚阈值 N%"
```

## 周报模板

```markdown
# [姓名] 周报 [日期]

## 本周关键结论（BLUF）
[一句话总结最重要的事 — 比一千字汇报更值钱]

## 本周完成
- [具体成果 + 数据，不只是"做了"]
- [关联到目标：本周该指标提升 X%]

## 下周计划
- [可量化目标，不写"持续优化 XX"]
- [明确产出物 + 时间节点]

## 卡点 / 风险
- [问题描述 + 已尝试方案 + 求助/已缓解]
- 不要"等老板看到再说"
```

## 月报模板（一页式）

```markdown
# [产品名] [月份] 月度回顾

## 关键指标对账（vs OKR）
| 指标 | 目标 | 实际 | 达成率 |
|------|------|------|--------|
| [北极星] | X | Y | Z% |
| [关键 KR] | X | Y | Z% |

## 三件最重要的事
1. [战略性进展 + 数据]
2. [影响 OKR 的关键事件]
3. [对下季度有影响的决策]

## 学到的（前瞻）
- [一个本月学到的关键认知 + 怎么影响后续]

## 下月聚焦
- [Top 1 优先级]
- [Top 2]
- [Top 3]
```

## 风险升级时机

```
什么时候必须升级（不能等）：

🔴 立即升级（24h 内）
- 影响 P0 KPI 的事件（DAU 跌 10%+）
- 安全/合规事故
- 关键依赖方变化（接口下线、合作方撤资）
- 跨部门冲突无法在 PM 层解决

🟡 当周升级（含建议）
- 目标偏离 > 20%
- 关键人员变动
- 重大需求变更
- 预算超支预警

🟢 月报披露
- 长期趋势
- 流程优化建议
- 知识沉淀
```

## 反面教训

```
❌ "我有 5 件事要汇报..."
   → 全列没重点 = 没汇报

❌ "听说用户不喜欢..."
   → 二手信息不可信，先验证

❌ "我觉得..."
   → 数据 + 推断 + 不确定性，三件套不能少

❌ "下周我会努力..."
   → 写出可验证的产出，不要写态度

❌ "出问题了，怎么办？"
   → 至少给 1 个建议方案，不要把问题原封不动抛回去
```
