# Gap Analysis — 功能差异分析知识库

> 售前接到客户需求清单（可能 50-500 条），要快速判断：
> "我们能做几条？做不了的怎么办？要不要继续投？"
> 区别于 `rfp-response`（被动应答客户问询）：本 Skill 是**主动盘点能力 vs 需求**。

---

## 一、4 级匹配标签

| 标签 | 含义 | 应对动作 |
|------|------|---------|
| ✅ **满足** | 现有产品开箱即可 | 标准应答 + 演示证据 |
| ⚠️ **部分满足** | 现有产品能解决 60%-90% | 明确边界 + 客户化定制范围 |
| 🔄 **替代方案** | 不直接做但有同等业务效果 | 替代方案 + 成功案例 |
| ❌ **不满足** | 当前产品做不到 | 定制开发评估 / 生态补齐 / 弃单 |

**铁律**：
- 客户的"必备需求"出现 ≥3 个 ❌ → 高风险，重新评估机会
- 客户的"必备需求"出现 ≥1 个 ❌ + 不解决 → 大概率丢单

---

## 二、需求拆解方法

### 2.1 三维度分类
```
按类型：
  - 功能需求（业务能力）
  - 非功能需求（性能 / 可用性 / 安全 / 合规）
  - 集成需求（与客户系统对接）
  - 服务需求（实施 / 培训 / SLA）

按优先级（MoSCoW）：
  - Must（必备，缺一不可）
  - Should（重要，可商量）
  - Could（期望，加分项）
  - Won't（明确不做，本期排除）

按复杂度：
  - 简单（开箱即用）
  - 中等（配置 / 集成）
  - 复杂（定制开发）
  - 战略级（产品 roadmap 调整）
```

### 2.2 拆解模板（一条客户需求 → 多条 SE 视角原子需求）

```
客户原文："系统需要支持权限管理"

拆解为原子需求：
  R1.1 用户角色管理（创建 / 修改 / 删除）   → ✅ 满足
  R1.2 角色权限映射（菜单级 / 字段级）       → ⚠️ 部分（字段级需定制）
  R1.3 多租户数据隔离                       → ✅ 满足
  R1.4 SSO 集成（客户已有 [系统]）          → ⚠️ 部分（需要适配协议）
  R1.5 审计日志（操作 / 登录 / 数据访问）    → ✅ 满足
  R1.6 权限审批流（申请 / 审批 / 撤销）      → ❌ 不满足（roadmap Q3）
```

## 三、Gap 评分模型

每个 ❌ 或 ⚠️ 都要打三个分（1-5）：

| 维度 | 1 分 | 5 分 |
|------|------|------|
| **影响度**（客户业务影响）| 几乎无影响 | 业务中断级 |
| **紧迫度**（客户时间压力）| 半年内可缓解 | 上线必备 |
| **工作量**（我方填补成本）| 1 周搞定 | 需要产品 roadmap |

**Gap 优先级 = 影响度 × 紧迫度 / 工作量**

```
高优先级（>= 5.0）→ 必须立即处理（定制 / roadmap 提前 / 客户接受替代）
中优先级（2.0-5.0）→ 可商量（替代方案 / 时间表）
低优先级（< 2.0）→ 客户化沟通后可缓做 / 不做
```

---

## 四、Gap 应对策略矩阵

```
                         紧迫度高             紧迫度低
                ─────────────────────  ─────────────────
工作量小    │  立即承诺定制开发      │  纳入产品 roadmap
（< 4w）    │  报价含定制费          │  客户分享 PR 给产品
            │
工作量中    │  评估资源后承诺        │  替代方案 + 客户案例
（1-3 月）  │  可能要谈商务条件      │  说服客户接受替代
            │
工作量大    │  生态合作（第三方）    │  诚实说明 + 时间表
（>3 月）   │  战略级取舍决策        │  风险与商务条件
```

## 五、Gap 决策树（继续投 vs 弃单）

```
开始：客户需求清单 + 我方 Gap Analysis 完成
  │
  ├── 必备需求中 ❌ 数量？
  │   ├── 0 个   → 🟢 继续投，按方案推进
  │   ├── 1-2 个 → 🟡 评估能否定制 / 替代
  │   └── ≥3 个  → 🔴 大概率丢单，重新评估
  │
  ├── 重要需求中 ❌ + ⚠️ 总数？
  │   ├── < 30%  → 🟢 良好适配
  │   ├── 30-50% → 🟡 商务谈判筹码
  │   └── > 50%  → 🔴 产品定位不匹配
  │
  └── 综合判断：
      高优先级 Gap 总数 ≥ 5 + 客户决策时间表 < 60 天
      → 弃单 / 转推 / 长期培育
```

## 六、Gap Closure Plan（缺口闭合计划）

针对每个高优先级 Gap，必须明确 4 项：

```
Gap ID：[编号]
描述：[客户需求 + 缺口具体内容]

策略：[四选一]
  ① 产品定制开发（含报价 / 工期 / 验收标准）
  ② 产品 roadmap 加速（与产品 PM 确认时间表）
  ③ 生态合作（第三方厂商 / 开源组件）
  ④ 流程绕过（不做这个功能但用 [Y] 达到效果）

负责人：[产品 PM / 售前架构师 / 销售]
时间表：
  - T+0：客户沟通预案
  - T+7：内部产品 review
  - T+15：客户确认接受方案
  - T+30：正式纳入合同

风险：
  - 如果 [假设] 不成立 → [备选方案]

商务条件：
  - 是否额外报价
  - 是否需要客户签 [SLA / 接受函]
```

## 八、客户验收口径同步

Gap Analysis 完成后，关键 Gap 必须**与客户书面确认**：

```
要求客户回签的 4 类项：

1. 部分满足 ⚠️ 项
   → 客户认可"满足部分"的具体边界
   → 避免上线后客户说"你们这没做到"

2. 替代方案 🔄 项
   → 客户认可替代方案达到业务目标
   → 写入合同附件作为验收依据

3. 定制开发承诺
   → 工期 + 报价 + 验收标准
   → 不允许口头承诺

4. 不做的 ❌ 项
   → 明确"本期不做" + "未来 roadmap 时间表"
   → 客户认可不做不影响整体验收
```

**输出物**：《[客户名] × [我方] 需求 Gap Analysis 与确认书》

## 九、Gap Analysis 执行流程

```
T-7 天：
  □ 收到客户需求清单（RFP / 招标文件 / 调研访谈记录）
  □ 拆解原子需求（一条客户需求 → 3-10 条 SE 视角原子需求）
  □ 分类（功能 / 非功能 / 集成 / 服务）
  □ 标优先级（Must / Should / Could）

T-5 天：
  □ 我方能力盘点（产品 PM 协同）
  □ 4 级匹配标签
  □ Gap 评分

T-3 天：
  □ 决策树评估（投 vs 弃）
  □ Gap Closure Plan 制定
  □ 商务影响评估（定制费 / 工期）

T-1 天：
  □ 内部 review（产品 + 商务 + 法务）
  □ 客户沟通预案

T+0：
  □ 客户沟通：透明展示 Gap Analysis
  □ 推进客户接受应对方案
  □ 关键 Gap 项书面确认
```

## 十、与其他 Skill 的边界

| 选择 | 用前者 | 用后者 |
|------|-------|-------|
| `gap-analysis` vs `rfp-response` | 主动梳理需求 vs 能力 | 被动逐条作答 |
| `gap-analysis` vs `solution-architecture` | 需求适配度评估 | 完整方案蓝图 |
| `gap-analysis` vs `build-vs-buy` | 客户的需求 vs 我方产品 | 客户的需求 vs（自建 / 买）通用决策 |
| `gap-analysis` vs `compliance-checklist` | 客户全维度需求 | 仅合规维度 |
