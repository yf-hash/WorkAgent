# 产品版本说明（Release Note）写作知识库

> 单一文档类型 | 受众：全员 + 客户 | 密级：可公开 | 形态：PPT 或 Word

---

## 核心原则

1. **用户视角**：所有功能描述都从"用户能做什么"出发，不写"内部模块 X 重构"
2. **按重要性排序**：新增功能 > 优化改进 > Bug 修复，吸引眼球的放前面
3. **诚实写已知问题**：发布前尚未解决的问题必须列出 + 规避方案
4. **升级风险显式化**：哪些场景升级要谨慎，哪些必须先备份
5. **不承诺下一版本时间**：路线图只描述方向，不给死时间

- 配置项 `xxx` 重命名为 `yyy`，升级时自动转换

- 升级失败回滚到 v1.5 的步骤参见部署手册

## 版本号规则

| 类型 | 示例 | 含义 |
| 主版本 | v2.0 | 架构重构 / 全面更新 / 不兼容变更 |
| 次版本 | v1.1, v1.2 | 功能补充 / 局部修订 / 向下兼容 |
| 补丁版本 | v1.1.1 | Bug 修复 / 安全补丁 |

---

## 用户价值描述规范

| 反例 | 正例 |
|------|------|
| "重构了用户认证模块" | "新增多因素认证，登录安全性提升" |
| "优化数据库索引" | "报表导出速度提升 3 倍（100W 行从 60s 降至 20s）" |
| "升级 Spring Boot 到 3.x" | "（一般不在 Release Note 中体现）" |

---

## 质量要求

| 维度 | 标准 |
|------|------|
| 用户视角 | 所有功能描述以"能做什么"开头 |
| 量化收益 | 优化项必须有可量化的数据 |
| 已知问题 | 必须列出，不能为空 |
| 升级注意 | 必须含检查清单与回滚说明 |
| 时间承诺 | 下一版本只说方向，不说时间 |

---

## 命名与密级

- **文件名**：`[产品名]【新版本号】版本说明_新版本号.[pptx|docx]`
- 例：`数据安全网关【v2.0】版本说明_v2.0.pptx`
- **密级**：可公开
