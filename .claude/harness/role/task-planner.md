# Task Planner — 任务分解规范

> 角色 meta-agent 生成执行计划时的**粒度与依赖规范**。目标是让 LLM 分解出的步骤"可执行、可展示、可跟踪"。

## 步骤粒度规则

### 一步 = 一次 command 调用
- ✅ `/prd --mode standard "AI 客服"` 是一步
- ❌ "写 PRD 并做用户研究" 不是一步（是两步）

### 步骤应有**明确产出物**
- ✅ "生成 PRD 文档"（产出 `./output/AI客服_PRD.md`）
- ❌ "思考产品定位"（无文件产出）

### 步骤应**独立可幂等**
- 同参数重跑，输出稳定
- 不依赖会话短期上下文之外的隐式状态

---

## 步骤数量

| 场景规模 | 建议步骤数 |
|---|---|
| 单点任务 | 1（不进入计划流程，直接执行） |
| 常见场景 | 2-4 |
| 典型工作流 | 5-6 |
| 大项目起步 | 6-8（**上限**） |

**> 8 步的信号**：需求太大，应该拆成两次会话。让用户先跑前 4-5 步，再基于结果决定后续。

---

## 步骤依赖

### 三种依赖类型

1. **参数依赖**：步骤 ② 需要用步骤 ① 的产出作为输入
   ```yaml
   - step: 2
     command: /prd
     depends_on: 
       - step: 1
         via: 上一步的 discovery 报告作为 --input
   ```

2. **决策依赖**：步骤 ③ 是否执行取决于步骤 ② 的结果（条件分支）
   - 计划展示时明确写"如果 X 则执行"
   - 到执行时用户可选择跳过

3. **无依赖（并行）**：多个独立步骤原则上不并行执行（保持顺序输出方便追踪），除非用户特别要求

### 表达方式

计划展示时用**→ 箭头**表示串行：
```
① /pm-clarify "客户想批量导入发票"
   ↓（产出 01-clarify-report.md）
② /pm-solution ./01-clarify-report.md
   ↓（产出 02-business-solution.md）
③ /prd --mode full --validate --input ./01,./02
```

---

## 步骤命名与描述

### 好的步骤描述（三要素）

`<命令> — <这一步做什么> → <产出什么>`

**示例**：
```
① /pm-clarify "客户想批量导入发票" — 识别 7 要素缺失并生成澄清报告 → 01-clarify-report.md
② /pm-solution ./01-clarify-report.md — 拆解业务方案（流程 + P0/P1/P2 + 权限） → 02-business-solution.md
③ /prd --mode full --validate — 撰写完整 PRD 并跑 4 类校验 → 04-PRD.md + validate.md
```

### 坏的步骤描述

- ❌ `① /prd` （没说做什么、产出什么）
- ❌ `① 帮用户写文档` （没说用哪个命令）
- ❌ `① 运行 pm-discovery 命令进行需求发现，涉及场景提炼、痛点识别、用户画像构建...` （太啰嗦，一句话足够）

## 参数注入规则

从用户输入中抽取参数注入 command：

| 用户提到 | 注入到命令 |
|---|---|
| 产品/项目名 | `<产品名>` 位置参数 |
| 客户名 | `--customer <name>` |
| 行业（金融/政务/医疗等）| `--industry <val>` |
| 模式关键词（简版/详细/企业级）| `--mode lite/standard/enterprise` |

**未明确时的默认值**：
- `--mode`：`standard`
- `--industry`：`generic`
- `--out`：`./output/<step-name>-<timestamp>.md`

**规则**：不问不必问的参数，用默认值 + 在计划里显式展示（用户看到不合适可以在 edit 阶段改）

---

## 上下文传递

多步骤间共享上下文的三种方式（优先级从高到低）：

1. **文件产出物**（最推荐）：前一步写文件，后一步 `--input <path>`
2. **会话内存**：前一步的关键结论存 memory，后一步读
3. **参数透传**：产品名/客户名/行业等在整个计划里保持一致

**禁止**：口头上"记得刚才那个"、"接着上面继续"——LLM 不同轮次上下文可能丢失，必须用显式载体。

---

## 反模式

- ❌ **步骤打包**：把 3 个 command 合并成"一步" → 无法单独重试
- ❌ **无产出步**：某步只是"思考一下"没有可交付物 → 无法验证完成
- ❌ **循环依赖**：③ 依赖 ⑤ 的产出 → 拆错了，重新分解
- ❌ **参数魔法数**：`/prd --industry fintech` 但用户没说金融行业 → LLM 幻觉，应该问
- ❌ **超 8 步计划**：应该分批，给用户"先跑前 N 步再看"的选择
