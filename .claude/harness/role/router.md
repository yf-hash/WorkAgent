# Role Router — 角色路由 SOP

> 所有 `roles/*/` 角色 meta-agent 的**通用交互流程**。角色 agent 正文只写角色特色，通用步骤引用本文件。

## 触发时机

用户敲 `/pm <需求>` 或 `@pm <需求>` 时，角色 agent 立即进入本 SOP。

---

## Step 1｜加载角色资产

**必读文件**（按顺序）：
1. `roles/<role>/manifest.yaml` — 能力清单 + workflow 触发词 + 委派规则
2. `roles/<role>/workflows.md` — 剧本详情（每个 workflow 的步骤解释）

**加载后建立三张表**：
- `capabilities`：能力域 → command 列表（用于动态编排）
- `workflows`：trigger 关键词 → 预设步骤（用于快速匹配）
- `delegate`：跨角色/跨 agent 委派规则

---

## Step 2｜意图识别

对用户输入做四类判断（按优先级）：

### 2.1 是否命中委派规则？
- 遍历 `manifest.delegate[].trigger`
- 命中 → 说明"这不在我的能力范围，建议转给 X"，让用户选择继续或转手

### 2.2 是否命中预设 workflow？
- 遍历 `manifest.workflows[].trigger`
- 命中 → 直接采用该 workflow 的步骤（跳到 Step 4）

### 2.3 是否单一 command 就够？
- 用户明确要求"帮我写 PRD"、"做一份 Gap 分析"等单点任务
- 是 → 直接调用对应 command，不走计划确认

### 2.4 否则进入动态编排
- 用户输入是复合需求（例："给 AI 客服做 PRD 并准备上线材料"）
- 进入 Step 3

---

## Step 3｜澄清（可选）

**只在信息不足时问**。判断标准：

必须澄清的场景：
- 目标产品/项目名称模糊（"帮我做个方案"）
- 场景无法定位（既像 A 又像 B）
- 关键参数缺失（无客户名做 /gap-analysis 无法执行）

**规则**：
- 最多问 3 个问题，一次性问完（用 AskUserQuestion 的多问题模式）
- 每个问题必须直接影响计划生成，别问"你希望怎样"这种开放题
- 已有默认值的不问（`--mode standard`、`--industry generic` 等）

**反例（不要这样问）**：
- ❌ "你想让我做什么？"（用户已经说了）
- ❌ "你是想要 A 还是 B 还是 C 还是 D 还是 E？"（选项过多）
- ❌ "还有什么补充吗？"（无穷发散）

---

## Step 4｜生成执行计划

参照 `task-planner.md` 的粒度规范，输出 3-8 步的执行计划：

```markdown
我识别到你要做「<场景名>」，我的执行计划：

① /command-a <arg>     — <一句话说明这步产出什么>
② /command-b <arg>     — <一句话说明这步产出什么>
③ /command-c <arg>     — <一句话说明这步产出什么>

产出物：
- <路径 1>：<内容>
- <路径 2>：<内容>

预计耗时：<X 分钟 / N 轮>
需要调整吗？（y 直接执行 / n 取消 / edit 手动改计划）
```

**格式要求**：
- 步骤编号用 ① ② ③（不是 1. 2. 3.）
- 每步"命令 + 一句话说明"，别只写命令名
- 说明要**产出导向**（写"生成 PRD 文档"，不写"运行 prd 命令"）
- 明确列出产出物路径

---

## Step 5｜计划确认闸门（唯一强制 gate）

用户回复选项：
- `y` / `确认` / `继续` → 进入 Step 6
- `n` / `取消` → 结束会话
- `edit` / 具体修改建议 → 回到 Step 4 修订
- 其他自由文本 → 视为修改指令，回到 Step 4

**gate 后自动执行，不再逐步询问**——这是本设计的核心承诺。

---

## Step 6｜依次自动执行

对每一步：

1. **调用对应 command**（用 Bash/Read/Write 等实际工具执行 command 的 harness）
2. **捕获输出路径**（后续步骤可能需要引用）
3. **短汇报**：`✅ ①/③ 已完成：<产出路径>`
4. **失败处理**：
   - 单步失败 → 停下来询问用户（继续 / 跳过 / 修复 / 中止）
   - 危险操作（security = high）→ 无论 gate 设置都必须确认

**不允许**：
- ❌ 在中间步骤反问"要继续吗"（已经在 Step 5 全局确认过）
- ❌ 悄悄改计划（如果发现计划错了，停下来告诉用户并重新走 Step 4）

---

## Step 7｜汇总与下一步

所有步骤完成后：

```markdown
✅ 「<场景名>」全部完成

产出物：
- <路径 1>
- <路径 2>

建议下一步（非强制）：
- <相关 command 或 workflow 提示>
```

---

## 错误处理策略

| 错误类型 | 处理 |
|---|---|
| Command 找不到（用户改动过仓库） | 打印缺失清单 → 让用户选替代品或跳过 |
| 参数解析失败 | 停下来问用户具体参数值 |
| 依赖前一步产出但前一步失败 | 中止后续步骤，汇总已完成 + 失败原因 |
| security = high 的操作 | 无论何时都必须 AskUserQuestion 确认 |

---

## 反模式清单

- ❌ 每步都问用户"要继续吗"（违背"计划一次确认"承诺）
- ❌ 计划里只有命令名没有产出说明（用户看不懂）
- ❌ 澄清阶段问 5-6 个问题（用户会烦，最多 3 个）
- ❌ 命中单一 command 时还生成 3 步计划（浪费用户时间）
- ❌ 出错后偷偷跳过继续（应该中止或询问）
